# 个人 Agent：结构化人物描述与选择性上下文

状态：根据用户反馈修订的设计。开放人物属性的手工管理、持久化、确认与版本历史已实施，见 [使用说明](../../guides/personal-profile.md)。自动提炼、选择性上下文和请求路由尚未实施。

## 1. 已明确的需求

1. 维护一个结构化的人物描述。
2. 人物属性不预先固定，可随交流增加、修改、细分和失效。
3. 根据当前请求选择需要的人物信息，不将整份描述默认加入上下文。
4. 普通知识问题不受无关任务描述、目标、进度或优先级影响。
5. 用户可以同时推进多件事，但这些事情不能成为每个回答的固定解释框架。

## 2. 人物描述的结构

采用开放的属性集合。属性名称、内容和层次可变，系统只固定信息管理所需的外层结构。

例如，交流中可能逐步形成下列属性：

```json
{
  "person_id": "local",
  "attributes": [
    {
      "id": "attr_1",
      "path": ["背景", "学习经历"],
      "value": "计算机方向研究生",
      "basis": "user_stated",
      "status": "active",
      "source_refs": ["message:example_1"],
      "scope": "person",
      "version": 1
    },
    {
      "id": "attr_2",
      "path": ["协作方式", "技术解释"],
      "value": {"preference": "先给例子，再展开原理"},
      "basis": "user_confirmed",
      "status": "active",
      "source_refs": ["message:example_2"],
      "scope": "person",
      "version": 1
    }
  ]
}
```

以上是结构示例，不代表用户已经提供这些具体信息。`背景`、`学习经历`、`协作方式` 等属性名由交流需要形成，不是必填字段或限制属性集合的 schema。值可为文本、数字、列表或对象，外层统一保存来源、确认状态、范围、版本和时间。

人物描述表达对人的持续认识。具体事项的任务要求、执行记录和成果分别存放，并通过引用联系人物属性；它们不被复制成一段永久注入的人物介绍。用户同时关心多个方向可表示为多个属性或引用，数量不限于一个。

不预设成长目标树、固定人设标签或必填身份表单。属性名称含义相近时建议合并，但不能把用户不同场景的表达自动视为同一偏好。

## 3. 人物描述如何更新

从对话中提取可能有长期价值的信息，以候选更新形式展示；当前消息可以直接支持本轮回答，持久化生效沿用显式确认机制。确认可以对一组更新统一进行，避免逐句确认。

新增属性不要求修改代码或数据库列。修改已有属性保留来源和版本，确认后的纠正替代旧的有效值。暂停某件事只改变相关信息，不推断用户永久改变身份或长期愿望。

区分：用户明确表达、用户确认的解释、Agent 的推测。推测可以帮助提出澄清，但不能作为确定人物事实注入执行模型。

每条属性有时间与适用范围。一次“这次简短回答”是本次表达要求，不能直接升级为长期偏好。“做代码审查时严谨一些”是场景偏好，不自动影响闲聊。

不从一次普通问题推断兴趣身份。例如询问强化学习概念，不自动创建“研究方向是强化学习”的人物属性。

## 4. 选择性上下文策略

先判断当前请求是否需要人物信息或事项信息，再读取候选信息。判断输入以当前消息和解决指代所需的近期交流为主，不预先把完整人物描述和所有任务塞给判断器。

### 请求与上下文的关系

| 当前请求 | 人物属性 | 事项或任务信息 |
|---|---|---|
| “什么是梯度下降？” | 默认不加入；已有明确相关的表达偏好可单独选择 | 不加入 |
| “结合我的基础解释梯度下降” | 选择相关知识基础与解释偏好 | 默认不加入 |
| “我适合从哪些方向准备实习？” | 选择相关经历、能力、诉求和现实限制 | 仅在确实相关时选择实习准备事项 |
| “继续昨天的实验分析” | 仅选相关背景 | 选择指代对应的实验、最新进展和材料 |
| “这周几件事怎么一起安排？” | 选择时间与资源约束 | 选择用户要求协调的多件事 |

关键判断是当前问题是否依赖这些信息，不仅是句式是否为问句。一般知识问答无需变成用户任务分析；个人决策问题可以需要人物属性而完全不需要执行计划。

不需要个人背景时，可以跳过人物召回；不需要事项背景时，可以跳过事项读取。没有相关命中时直接正常回答，不强行拼接看似相关的条目。

### 每条信息的选入条件

1. 与当前请求有明确关系，或用户直接要求使用。
2. 已生效且来源、范围、版本校验通过。
3. 在当前时间与场景下仍适用。
4. 对理解或回答有实际作用，符合上下文预算。

词项相似度只能用于寻找候选，不能单独决定注入。人物属性、事项背景和工具权限分别处理，人物描述不产生新授权。

## 5. 上下文组装

每次请求独立组装：

```text
当前请求
  → 识别所需背景及指代
  → 按需选择人物属性 / 对应事项 / 相关材料
  → 校验状态、来源、范围和时效
  → 按预算组装最少必要上下文
  → 回答问题或执行已授权行动
```

普通问题的输入可只含当前问题及理解它所需的近期交流。个人问题再增加选中的人物属性；事项续接才加入对应事项的描述与进展。

人物信息作为带来源的背景材料，不写成系统层的人设指令。任何保存偏好都不能覆盖用户本轮要求。

选择性也适用于会话历史：历史任务描述不因处于同一会话而整段默认拼接。需选择能解释当前消息的片段；“继续”“刚才那个”依赖的必要历史仍应保留。用户说“另外问个问题”时，应重新判断关联。

输出前检查是否把无关旧任务写进回答，是否用推测当作事实，是否把知识提问误变成行动计划。必要时重新生成不受无关背景影响的回答。

## 6. 用户可检查的界面

提供“关于我的认识”入口，以可展开的属性结构显示人物描述。用户能编辑、合并、删除属性，查看依据和确认情况。没有值的未知属性不要求用户填满。

每次回答可展开查看“本次使用的背景”，展示选入的属性与事项引用；没有使用时显示“未使用人物或事项背景”。这用于核对上下文选择，不暴露内部推理。

多事项列表作为需要时查看或继续的协作入口。用户可以用自然对话更新多件事，但首页不要求先选任务才能提问。

## 7. 现有项目需要调整的地方

当前 `agent.runner` 对多数非简短问候请求采用任务执行入口，生成计划并在决策循环中加入计划和执行记录；`AgentMemory` 按文本召回 active 记忆。两者尚未实现本设计要求的开放人物属性与完整选择性上下文策略。

后续应优先增加请求所需背景的判断与轻量回答路径，使普通问题不必先构造执行计划。然后增加人物属性的保存、候选更新、核对，以及精确选择与审计。现有长任务恢复、预算和研究工作流可以继续使用。

即使人物描述保存为 JSON、Markdown 或 SQL 记录，仍须逐条可寻址、可校验，不能只保存整份长文并全量注入。最终存储与接口细节在本设计确认后制定。

## 8. 验收情境

- 同一用户新增不同类型属性，无需增加固定字段。
- 已有实验、组会、求职背景时，问“什么是梯度下降”仍得到正常概念解释，不夹带任务安排或求职建议。
- 问“结合我的基础解释”时，只使用相关基础及表达偏好。
- 同一会话转到无关知识问题时，旧任务描述不被默认带入。
- 问“继续实验”时选择对应事项，而不丢失必要背景。
- 本轮要求“详细解释”时，不受旧的简洁偏好压制。
- 用户纠正某个人物属性后，后续请求采用已确认的新版本。
- 未确认的推测不作为确定事实参与个人建议。
- 回答可以核对所用背景，通用问题允许选入零条。

## 9. 设计边界

此版以人物描述的开放结构和选择性使用为主，多事项跟进作为按需背景能力。定时通知、主动后台执行和新工具建设另行设计；本草案不启动这些操作。
